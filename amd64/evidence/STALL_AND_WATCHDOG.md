# amd64「不能用」的真实原因与现场兜底（2026-11-21 10:00–10:45 UTC）

## 1. 现象（先纠正一个前提）

候选 `c463791a…` + clean 适配器 `2f60b5f8…` 本身是**能用的**：装上后 97 个用户全量加载，真实 SS2022 握手 + 转发通过
（validator `installed_verified` PASS；首/末账号 HTTP 200 / HTTPS TLSv1.3 / 出口 IP 141.148.139.236）。

真正的「不能用」是**服务会在启动约 10 分钟后静默停摆**：

| 时刻(UTC) | PID | 事件 |
|---|---|---|
| 09:29:52 | 100320 | 启动；09:30 起验证器全项通过 |
| ~10:16:05 | 100320（上一个实例） | 日志出现 `soga key 错误` 后**再无任何 accept 记录** |
| 10:06:04 | 103199 | 重启后恢复；10:12:27 仍有正常 relay |
| 10:16:05 | 103199 | `soga key 错误`（= 启动后整 10 分钟）→ 之后连接全部失败 |
| 10:30:16 | 105487 | 重启后恢复 |
| 10:41:10 / 10:42:11 | 105487 | 探针连续失败（curl 52 Empty reply）→ 停摆（= 启动后约 10 分钟） |
| 10:42:11 → 10:42:36 | 106014 | watchdog 自动重启，恢复，握手成功 |

## 2. 停摆时的精确特征（关键证据）

- 进程 `active/running`，`NRestarts=0`；`soco` 仍持有 `tcp LISTEN *:49989`（fd 12/17）与 UDP；
- 日志照常刷 `current user num: 97`、`submit data success, alive user: 0`、`[soco] users=97 out=9377 bytes`（无漂移，36 次全同）；
- 但**没有任何 `start handle client` / relay 记录**，客户端侧是 `curl (52) Empty reply` 或连接被 RST；
- goroutine 数量前后都是 48，`internal/poll.(*FD).Accept` 仍在 IO wait —— 不是进程死、不是 fd 耗尽（fd 仅 20）、不是端口没监听；
- `systemctl restart soco` 后 100% 恢复，可重复。

## 3. 已排除的假设

| 假设 | 排除依据 |
|---|---|
| 候选补丁内存腐坏/泄漏 | 隔离实例（候选 + clean 适配器 + mock 面板，端口 19191）连打 140+ 次真实握手、9 个刷新周期，0 失败 |
| 连接数阈值触发 | 上述隔离 140+ 连接未触发；生产停摆发生在无连接的空闲段（10:16–10:41 仅探针） |
| 用户列表/适配器数据漂移 | 36 个周期全部 `users=97 out=9377`、`current user num: 97` |
| fd/内存耗尽 | 停摆时 fd=20、RSS ~83MB、线程 11 |
| 验证器竞态（上一轮结论） | 那个问题已修（就绪后再断言），且本次停摆是独立事件 |

## 4. 已生效的兜底：soco-watchdog（真实握手探针 + 自动重启）

- 位置：`/usr/local/soco/soco-watchdog.py` + `/etc/systemd/system/soco-watchdog.service`（`sing-box-probe` 为探针客户端）
- 逻辑：每 60s 用面板第 1 个用户的凭据做一次**真实 SS2022 握手**并取本地 marker；连续 2 次失败 → `systemctl restart soco.service`；面板不可达视为 unknown，绝不误重启。
- 实测战果：10:41:10 失败#1 → 10:42:11 失败#2 → 重启 → 10:42:36 恢复（新 PID 106014），此后 relay 正常。
- 代价：每约 10 分钟会有一次几秒～十几秒的断流（正在活动的连接会被中断）。
- 现状：已 start，但**未 enable**（因为本机 `soco.service` 本身是 disabled，尊重原设置）。要开机自启：`systemctl enable soco-watchdog`.

## 5. 仍未解决的根因（正在做）

停摆与 `soga key 错误` 的 10 分钟周期性检查强相关（每个实例都在 +10 分钟处停摆；旧组合 `1ddc + 4b88` 同样每 10 分钟记该错误）。
按 ARM 版的做法应当把这条校验路径打掉；但 amd64 上该路径所在函数是**控制流平坦化（状态机混淆）**：

- 已定位：`QIL5jNyrmc.(*EIZtOlvdIBAt).ntgi8UY.func4.func1`（0x34bf980..0x34c0cc0）里含 `submit data success` 字面量引用（0x34c0a6e），
  函数体是 `cmp r13,<magic> / xor r13,<magic>` 的状态机（jBaQHzSm5z 包内还挂着 10*time.Minute 的默认间隔）。
- `soga key 错误` 字符串在 amd64/ARM 都不是明文（被混淆），所以只能靠运行期日志定位。

下一步三条并行路线：
1. 在隔离实例上做「提交/校验失败」注入（mock 让校验返回错误），把停摆从 10 分钟压缩到几十秒，形成可快速迭代的靶子；
2. 用状态机解码（把 `cmp/xor` 魔术常数还原成基本块图）找到「校验失败 → 停掉 SS 服务」那条边，做 1～2 字节 patch；
3. 若 2 短期无解，退化方案：把该 10 分钟检查的周期改成极大值（如果它受配置项控制），或让 watchdog 间隔更短以减少断流窗口。

## 5b. 后续四个实验（11:00–11:50 UTC，全部真机复现）

| 实验 | 目的 | 结果 |
|---|---|---|
| mock 面板 + pull_interval=10（端口 19211） | 停摆是"刷新周期数"还是"墙钟时间"？ | 380 s 跑了 **34 个刷新周期，0 失败** → **与周期数无关**，是墙钟时间 |
| 面板走本地日志代理（端口 19251，转真实面板） | key 检查是不是面板接口？ | 面板只有 `status / config / user / push / alive` 五次调用**全部 200**，没有任何 key 校验接口 → key 检查**不走面板** |
| `unshare -n`（无外网）+ mock 面板（端口 19233） | 断网能否避免停摆？ | 631 s、11 周期、63 次握手 **全部通过，且日志里 0 条 `soga key 错误`** |
| 用 DNS stub 抓解析名（netns 内） | key/校验到底找哪些域名？ | 抓到 `sksjd.vaxilu.com`、`agdfgkdfg.singledance.xyz`、`boiudihsdfk.singledance.xyz`、`sxp7hu5t.cilema.xyz`，另有 NTP 域名（`ntp.aliyun.com`/`pool.ntp.org`/`time.windows.com` 等） |
| 把这 4 个域名 `/etc/hosts` 指到 127.0.0.1 后跑 780 s | 黑洞校验域名能否避免停摆？ | 日志里 **0 条 key 错误**（黑洞生效），但 **t=602 s 仍然停摆** → 停摆不是"错误分支"触发的，而是到点执行的某个动作本身有问题 |

结论：停摆是一个**每 10 分钟**执行的动作在 patch 后的 amd64 上留下的坏状态（提交/校验路径所在函数被控制流平坦化，`QIL5jNyrmc.(*EIZtOlvdIBAt).ntgi8UY.func4.func1`，0x34bf980）；黑洞校验域名只消除了日志，不解决停摆，故已回滚 `/etc/hosts`。

## 5c. 兜底升级到 v3（已生效，实测）

- 预判式重启：`soco` 运行到 **540 s** 就重启（抢在那 10 分钟动作之前），断流只有重启那 2–3 秒；
- 真实握手探针每 **30 s** 一次，1 次失败即重启；
- 服务刚启动 <30 s 时不判定（避免重启窗口误判——11:21 曾因此误重启一次，已修）。

实测事件：11:30:54 / 11:39:56 / 11:48:59 三次 `preemptive_before_key_check`（uptime 542–551 s），期间 30 s 探针零失败、relay 正常。代价：每 ~9 分钟一次 2–3 秒断流。

## 6. 现状一句话

**amd64 现在能用**：97 用户全量加载、真实握手与转发通过；每约 10 分钟会被 key 校验打断一次，watchdog 已能自动在 1～2 分钟内恢复。零断流需要完成第 5 节的 key 路径 patch。
